# Setup internals

What each setup step does on the Mac, what it writes and where, where each secret lives, and how `parent-recap uninstall` reverses it. It's for maintainers: when a setup step starts writing something new, add it here and teach uninstall to remove it, so the two stay in step. The family-facing steps are in [skills/setup/SKILL.md](../skills/setup/SKILL.md); the secrets and the data flow, in [SECURITY.md](../SECURITY.md).

## Setup's record

Every step that creates something adds it to `~/.family/install-record.json` (owner-only), through `family_brief.install_record`:

| Kind                 | Added by                                                                     | Value                                                                                                                               |
| -------------------- | ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `program`            | `install.sh`                                                                 | The program folder, `~/ParentRecap/app` by default: a link to the running version's folder ([Versions](#versions))                  |
| `versions`           | `install.sh`                                                                 | `~/ParentRecap/versions`, the running version's folder and the previous version's, kept to switch back to                          |
| `logs`               | `install.sh`                                                                 | `~/ParentRecap/logs`                                                                                                                |
| `runtime`            | `install.sh`                                                                 | `~/ParentRecap/runtime`, which holds Parent Recap's pinned Python and Node                                                          |
| `plugin`             | `install.sh`, run from `~/ParentRecap/plugin`                                | That plugin copy                                                                                                                    |
| `baileys`            | `install.sh`, before its `npm ci` runs                                       | `~/ParentRecap/baileys`, the Baileys tree the Linked Device runs on                                                                 |
| `command`            | `install.sh`, `install.ps1`                                                  | `~/ParentRecap/bin`, the folder holding only `parent-recap`                                                                         |
| `user-path`          | The same                                                                     | That folder, as put on the PATH: a marked line in `~/.zprofile`, or on Windows an entry in the user's PATH under `HKCU\Environment` |
| `codex-skill`        | `install.sh --codex`                                                         | `~/.agents/skills/parent-recap-setup` and `parent-recap-manage`                                                                     |
| `launchd`            | `parent-recap schedule install`                                              | Each job's plist in `~/Library/LaunchAgents`                                                                                        |
| `keychain`           | Storing a Gmail App Password                                                 | The Keychain account, `gmail-imap-<address>`                                                                                        |
| `wilma-cli`          | Installing the wilma CLI: the setup page, or `parent-recap setup wilma`      | The CLI's folder, `~/ParentRecap/wilma` by default                                                                                  |
| `wilma-profile`      | Signing in to Wilma on the setup page, or in `setup wilma`'s Terminal window | The profile's id, `<Wilma address>\|<username>`, never the password: tells setup's from the family's own                            |
| `claude-plugin`      | `get.sh --claude`, or the setup page once Welcome is saved with Claude       | `parent-recap@kinlace`                                                                                                              |
| `claude-marketplace` | The same                                                                     | `kinlace`                                                                                                                           |

The last three go in only when setup installed them: a Wilma profile, plugin or marketplace that was already there in any form (such as a `kinlace` marketplace from an unzipped release) isn't recorded, so uninstall leaves it. `get.sh --claude` runs before the program is installed, so it writes its two kinds into the file itself.

Installs from 0.4.1 and older have no record. Uninstall then looks in the places listed below, says the record is missing, and lists what it found for the family to check before confirming. With or without a record, it checks that each item is this install's before it lists it for removal.

## Versions

`install.sh` (on a Mac and on a Linux server; `install.ps1` on Windows doesn't) installs each release beside the running one and switches to it only once that install finished (ADR 0047, `family_brief/versions.py`):

- Each version lives in a folder of its own, `~/ParentRecap/versions/<version>.<random>`: the program's files, its `.venv` built on the pinned Python, `VERSION`, and `RUNTIMES`, the folders in `~/ParentRecap/runtime` its venv and the wilma CLI run on. The install builds it there while the running version goes on as it was; one that fails or is cut off before the switch leaves the running version and nothing switched, and its folder is removed (by the install itself, or by the next one's switch).
- `~/ParentRecap/app` is a link to the running version's folder, and the one path everything outside the program starts it from: the evening jobs' plists, the Linked Device's always-running job, Parent Recap Settings and Check, and `~/ParentRecap/bin/parent-recap`. A version's own scripts name its folder, so the program writes paths in a version's folder as their path through `app` (`versions.stable`). An update that doesn't change a job's definition leaves its plist as it was, and macOS has no new background item to announce.
- The switch points `app` at the new version in one step (a new link renamed over the old one), keeps the version it pointed at before as `~/ParentRecap/versions/previous`, one version deep, and removes every other version's folder and every runtime folder neither of the two names in `RUNTIMES`. The same version installed again (as manage does to add Google's packages) replaces its own folder and keeps the different version before it. Then it runs the version's steps below (the record, the command, the wilma CLI, the Baileys tree, Settings and Check, the evening jobs) from `app`, and starts a running Linked Device again (`launchctl kickstart -k`), so it runs the new version.
- `parent-recap switch-back` points `app` at the previous version and keeps the one it switched from as the previous one, so running it again switches forward. It then runs that version's own steps from `app` (`command_path`, `setup_wilma update` and `baileys_install install`, which put back the wilma CLI and the Baileys tree it pins, and on a Mac `program_entries` and `schedule_update`), and starts a running Linked Device again. Without a previous version it says so and changes nothing.
- `parent-recap update` (on a Mac, run from an installed release; `family_brief/update.py`) reads the version the `stable` branch holds and, when it's higher than the running one, downloads that tag's release zip and its `.sig` into `~/ParentRecap/update/download.<random>`, verifies the signature against the keys the program ships, checks the zip holds that version, puts it in `~/ParentRecap/plugin` (as the install line does, the copy before kept until the update is done) and runs its `install.sh` as a file, with `PARENT_RECAP_UPDATING` set so nothing asks for a password (an older version's wake isn't moved), unless the release needs the family and they started it (below). It runs the running version's `doctor` before and the new one's after; a check only the new one fails switches back as `switch-back` does, with the plugin copy before put back. The download's folder goes when it ends, whatever happened. Its state (the last look, its result, a version that failed) is `~/ParentRecap/update/state.json`, outside the versions, and each step is a line of `~/ParentRecap/logs/update.log`. Uninstall removes `~/ParentRecap/update`, but only if it holds nothing but the state and download folders, and the log with the logs. The evening job runs the same update by itself (`update.evening`, #915) once its run has sent the Brief or decided to send nothing (a catch-up only once it sent one; never a run by hand, `schedule run-now`, a dry run, Weekend Picks or a Hosted Household), still holding `~/.family/run.lock`, so `schedule_update` leaves the jobs' plists as they are and adds no background item. It installs a version only on an evening at least a day after this Mac first saw it on `stable` (`seen` in the state; 22 hours, so the next evening's run counts even when it starts a little sooner after its time), never tries again a version that failed (`failed`), and whatever it does, the run's exit and `last-run.json` stay as the run left them. What came of it is kept in the state for the next Brief that is sent (#916): the version it updated to (`tell_updated`), or the version that failed to download whole, verify, install or pass its check and the one still running (`tell_failed`, once per version: `told_failed`). That Brief says so at its top, the first time also that Parent Recap updates itself (`told_updates_itself`), and once it is delivered the note is cleared. A Hosted Household's or a Windows computer's Brief never says it.
- A release that needs the family at the computer (#918) says so in `release.json` at the zip's root, where the signature covers it: `background_from`, the lowest version that can take it in the background, and `asks`, a sentence in `en`, `fi` and `zh` on what the family will be asked (CONTRIBUTING.md, "A release that needs the family"). The program reads it only from the zip it verified, and only the newest release's, which carries the value of the releases before it. On a version below `background_from` the evening run doesn't install it: it downloads and verifies the zip once, keeps the version, the value and the sentences in the state (`waiting`), and on later evenings doesn't download that version again; its outcome is `needs-family`, which is no failure (`failed` and `tell_failed` stay as they were). The next Brief that is sent says once per version that the update is waiting, what it asks, in the Recipient's language or English, and how to start it (`told_waiting`); `doctor`'s Updates line and the setup page say the same, the page with Update now. Started by the family, with `parent-recap update` or Update now, its `install.sh` runs without `PARENT_RECAP_UPDATING`, so `schedule_update` installs the jobs again and opens macOS's administrator dialog; a dialog that's closed keeps what the older version had, and the new version's `doctor` decides as for any update. A file that can't be read refuses the release. With updates turned off nothing is downloaded, so the Brief says only that a newer release is out.
- Updating by itself is one setting, the config's `updates.enabled`, on unless the family turned it off (#917): a config that says nothing of it, a new one or one from before the setting, has it on. The switch on the setup page's Finish and `parent-recap update on|off` save it through `setup save` (`update.set_enabled`); it is in the config, outside the versions, so an update and a switch back keep it. Turned off, the evening run only looks (`update.look`): it reads the version `stable` holds, that one request, downloads nothing, and keeps a newer version for the next Brief to say is out, once per release (`tell_available`, `told_available`), with how to get it. `parent-recap update` and the page's Update now install the newest release whenever the family asks, on or off. `update.status` is the update state as the page, `doctor`'s Updates line and the report a family copies from the page show it (the version, on or off, the last look and its result), read from the state without asking any host; where the program doesn't update itself (Windows, the hosted version, a program not run from an installed release) it says so, the page shows the version alone, `update on|off` explains and saves nothing, and the evening run asks no host. A page opened again at Finish stays open where the program updates itself, for the switch and Update now.
- An install from before versions, the program in `~/ParentRecap/app` itself, is moved to `~/ParentRecap/versions/<version>.before` by the first install after it, which writes its `RUNTIMES` as every folder `runtime` held then. Its venv names `app`, so it runs again once `app` points at it.
- The config, the state, the Keychain items, the Linked Device's pairing and the archive aren't in a version's folder, and an install, a switch and a switch back leave them as they are. The wilma CLI (`~/ParentRecap/wilma`) and the Baileys tree (`~/ParentRecap/baileys`) are shared by the two versions: each install, and each switch back, puts in the ones the version now running pins.
- On the hosted server (ADR 0035, ADR 0036) each deploy is installed into a folder of its own, `PARENT_RECAP_HOME=/usr/local/lib/parent-recap/<deploy>`, which holds one version this way; `current` and `admin rollback` switch between deploys as before.

### What an install writes outside Parent Recap's folder

Everything else an install writes is in `~/ParentRecap` (or `PARENT_RECAP_HOME`). Outside it:

- `~/.family` (700) and setup's record in it, `~/.family/install-record.json`.
- The PATH entry for `parent-recap`: a marked line in `~/.zprofile` on a Mac, or a link in `~/.local/bin` on Linux.
- On a Mac, `~/Applications/Parent Recap Settings.app` and `~/Applications/Parent Recap Check.app`.
- On a Mac whose evening Brief is scheduled, the jobs' plists in `~/Library/LaunchAgents` (`com.parentrecap.daily`, `com.parentrecap.weekend-events`), rewritten only when their definition changed, and the wake schedule (`pmset repeat`, through macOS's administrator dialog) when an older version's wake is moved.
- For a Household with a Wilma sign-in, the wilma CLI's `~/.config/wilmai/config.json` and the keychain items `wilma config secrets auto` moves its passwords to (Connect: Wilma, below).
- With `--codex`, `~/.agents/skills/parent-recap-setup` and `parent-recap-manage`.
- pip's cache (`~/Library/Caches/pip` on a Mac, `~/.cache/pip` on Linux), as pip keeps one; the downloads of the pinned Python and Node, and npm's cache, go in temporary folders that are removed.

The evening job and `doctor` read it with `find-generic-password -w`, giving up after 5 seconds: an item an earlier version stored with Python's `keyring` makes macOS ask for the Keychain password first, which nobody answers at night. `doctor` tells such an item apart from a missing one and says to store it again.

Uninstall checks a Keychain item is there with `security find-generic-password` without `-w`, so it never reads a secret, and prints only the service and account.

## How an update works

On a Mac, for a program run from an installed release (ADR 0047, `family_brief/update.py`; not on Windows, and not for a Hosted Household). [Versions](#versions) has the detail of each step and the state's keys; [SECURITY.md](../SECURITY.md#how-parent-recap-updates-itself) says the same to a family and lists the hosts. The steps, in order, each a line of `~/ParentRecap/logs/update.log`:

1. **Start.** The evening job starts it (`update.evening`) once its run has sent the Brief or decided to send nothing, still holding `~/.family/run.lock`; a catch-up only once it sent a Brief; never a run by hand, `schedule run-now`, a dry run or Weekend Picks. The family starts the same update with `parent-recap update` or the setup page's Update now, which starts nothing while a Brief is being made and says so.
2. **Look.** One GET to `raw.githubusercontent.com` for the version `stable` holds. It writes `~/ParentRecap/update/state.json` (`last_look`, `last_result`, and `seen`: when this Mac first saw that version). A version that isn't higher than the running one ends it here. With `updates.enabled: false` the evening's update always ends here (`update.look`), keeping a newer version for the next Brief (`tell_available`).
3. **Wait.** The evening's update goes on only when this Mac first saw the version at least a day ago (22 hours), it didn't fail before (`failed`), and it doesn't wait for the family (`waiting`). One the family started skips all three.
4. **Download.** The release's zip and its `.sig`, from `github.com` and where it redirects among `update.HOSTS`, into a new `~/ParentRecap/update/download.<random>`. A download that is cut off, or redirected elsewhere, ends it.
5. **Verify.** `/usr/bin/ssh-keygen -Y verify` against the keys in `family_brief/release_signers` (`release_signature.py`). Then it unpacks the zip inside the program, into the download's folder, and reads the version inside: it must be the one asked for and higher than the running one. A zip that fails either is deleted with its folder.
6. **Does it need the family?** It reads `release.json` in the unpacked zip. On a version below its `background_from`, the evening's update keeps the version and what it asks in the state (`waiting`) and ends; one the family started goes on, with dialogs.
7. **Check before.** The running version's `doctor`, for the checks it already fails.
8. **Install.** It moves `~/ParentRecap/plugin` into the download's folder, puts the unpacked release in its place, and runs `/bin/bash ~/ParentRecap/plugin/install.sh` (with `--codex` when the record has the Codex skills), with `PARENT_RECAP_UPDATING=1` unless the family started a release that needs them. The installer does what "Connect: install" in [Each step](#each-step) says: a new Python or Node if the release pins one, the version's folder and its venv, the switch of `~/ParentRecap/app`, the record, the command, the wilma CLI, the Baileys tree, Settings and Check, and `schedule_update`, which in the evening's update leaves the jobs' plists and the wake as they are. An installer that fails before the switch leaves the running version; the plugin copy before is put back.
9. **Check after.** The new version's `doctor`. A check it fails that the version before didn't, or a `doctor` that didn't run, switches back as `parent-recap switch-back` does, puts the plugin copy before back, and keeps the version as `failed`.
10. **End.** The download's folder is removed, whatever happened. The evening's update keeps what came of it in the state for the next Brief that is sent (`tell_updated`, or `tell_failed` once per version; a download that failed is no `tell_failed`, and is tried again the next evening, as is a zip that didn't verify), and the run's exit and `last-run.json` stay as the run left them.

What it leaves on the Mac beyond what the installer writes ([What an install writes outside Parent Recap's folder](#what-an-install-writes-outside-parent-recaps-folder)): `~/ParentRecap/update/state.json` and `~/ParentRecap/logs/update.log`. Uninstall removes `~/ParentRecap/update`, but only if it holds nothing but the state and download folders, and the log with the logs.

## How uninstall works

`parent-recap uninstall` first lists everything above that it finds, and removes nothing. Something in those places that isn't this install's stops it, before it removes anything: a launchd job with Parent Recap's label that runs another program, a config Parent Recap didn't write, a program folder or Codex skill of the same name that isn't Parent Recap's, a command folder holding other files, an app in `~/Applications` named Parent Recap Settings or Parent Recap Check that the install didn't make, or a run that's going. A config is Parent Recap's when it reads as one and either has `gmail` or `email` settings or has no keys but the config's own, as one from a setup stopped before the Recipients were saved does; unreadable YAML, or a key Parent Recap doesn't use with neither of those, stops it. Files that only share a folder with Parent Recap's, such as a note in `~/ParentRecap`, don't stop it: it lists them under "Left as it is" and doesn't touch them.

It removes only after the family confirms: `--confirm` with `--keep-archive` or `--remove-archive`, or, run in Terminal, its own two questions. The archive is the dated files (`<date>.md`, `<date>.raw.json`) in the archive folder and the Weekend Picks folder, and nothing else in them. The list `ai-filter-report --held-back` writes in the archive folder (`held-back-list.txt`) is made from the archive again each time, so it goes whether the archive stays or not. It removes in this order: the launchd jobs (so nothing starts mid-way), the wake schedule, the Keychain items, the Wilma sign-ins and the wilma CLI, Claude Code's plugin and then its marketplace, the Codex skills, the plugin copy, the archive if chosen, the config and state, the logs, Parent Recap Settings and Parent Recap Check, the command, the program, and the record last, which stays if anything couldn't be removed so the next try still knows what's left. Before it starts, it adds every Keychain item it found to the record, so one macOS refused to delete is found again after the config that named it is gone. Of the folders setup makes (`~/ParentRecap`, its `weekend_events/`, `~/.family`), those left empty are removed too; a folder of the family's own that held the archive stays. It never touches the family's accounts; it ends with where they can delete the App Password and the Google Calendar access themselves.

On Windows it is run in PowerShell, as `parent-recap uninstall`, and removes the same things where Windows keeps them: the Task Scheduler tasks named `Parent Recap <job>`, the Credential Manager credentials named `Parent Recap/<name>`, which Windows deletes without asking, the two shortcuts in the Start menu's `Parent Recap` folder, and `install.ps1`'s folders in `%LOCALAPPDATA%\ParentRecap` (the program, `runtime` with its pinned Python and Node and the `.download` folder a cut-off install leaves, `logs`, `wilma` with npm's `node_modules` and its wrappers for each command the package names, such as `wilma`, `wilma.cmd` and `wilma.ps1`, and the `plugin` copy the pasted line downloads). Those are found in `%LOCALAPPDATA%\ParentRecap` also when the record is gone. There is no wake schedule to cancel: the tasks wake the PC themselves, and "Allow wake timers" is the family's own setting, listed under "Left as it is". Windows doesn't let a program, or the Python it runs on, be removed while it runs, so the program and `runtime` go last, from a hidden PowerShell that uninstall starts, outside its own process: it waits for uninstall to end, removes them, trying again for a minute while the launchers that started uninstall end too, then removes `%LOCALAPPDATA%\ParentRecap` if it's left empty. Uninstall says they go once it has ended. If that PowerShell can't start, they're reported as not removed and the record stays.

After it, `~/.family/config.yaml` is gone, so setup starts again from the beginning on the same Mac or PC.
