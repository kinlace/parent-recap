# eVaka is read through its citizen API, with a stored password

Public daycares in Espoo, Tampere, Turku, Oulu and eight towns of the Tampere region run on eVaka, the cities' open-source early-childhood education system (`espoon-voltti/evaka`), and a daycare's excursions, photo days, closed days and reservation deadlines are what a chat at pick-up tends to miss (#766). eVaka has no calendar feed and no published API, but its citizen web app reads everything as JSON from `https://<host>/api/citizen/` over a cookie session, and since February 2025 every city lets a guardian sign in with an email and password of their own, with no CAPTCHA or second factor: `POST /api/citizen/auth/weak-login`, a JSON body `{"username", "password"}` and the header `x-evaka-csrf: 1`, which sets the session cookie `evaka.eugw.session` (read from the code at 2ad3203f, not tried on an account: no one on the team has one). So the eVaka Source signs in as the web app does, then reads `children`, `calendar-events` and `reservations` for the next four weeks, since a daycare announces closed days and trips well ahead (#777). Each city is its own host with its own sessions, so a Household has one eVaka sign-in per city, as it has one Wilma sign-in per town (#647); the known cities and their hosts are a small table in the collector, and a city not in it can be given by its host. The password is kept in the system's secret store (ADR 0020, ADR 0030), as Eepos's is (ADR 0038), and the rest of the sign-in, the city and the email, in the config. Of the children eVaka lists, which come with their unit, group and placement, only the ids and names are read. The first slice reads events, closed days and the reservation deadline, and a maintainer adds a sign-in from a terminal (`parent-recap setup evaka`), the password typed at the secret store's own prompt; messages, holiday questionnaires and steps on the setup page and the hosted sign-up come later (#768).


**2026-11-05: messages are read too (#786).** The evening run also reads the guardian's received messages, `messages/received?page=` (ten threads a page, the latest first), back to `evaka.lookback_hours`, and each message the daycare or the city sent since the last run becomes a Message for the Kid its thread names, told once; the family's own messages, from an account of type `CITIZEN`, aren't. A sensitive thread comes to a password sign-in as a stub (`CitizenMessageThread.Redacted`: sender, time of its last message, unread), so its Message has no text, and its Source withholds it: the Brief names it under Held-back messages with its link, and no model is asked about it, even with the AI filter off (ADR 0013). A message to 15 or more guardians' accounts, or from the city, counts as sent to everyone; only that count is kept, never the other guardians' names. Nothing is written: nothing is marked read, nothing is answered. Messages that can't be read leave the events, and the coverage line says eVaka was partly read. The response shape is from `MessageControllerCitizen.getReceivedMessages` and `Message.kt` at espoon-voltti/evaka@2ad3203f.

## Considered Options

- **Suomi.fi strong sign-in, as the family signs in on the web.** Rejected: it needs the parent's bank credentials or mobile ID each time, which an evening run can't have. It would also see more than the Brief needs: decisions, fees and pedagogical documents.
- **Scraping the citizen pages.** Rejected: the pages are drawn by the web app from the same JSON, so the JSON is both easier to read and less likely to change than the markup.
- **Running eVaka's own frontend client.** Rejected: the generated TypeScript client needs the whole frontend build. Three GET endpoints, read by a module beside the Eepos collector and tested against a fake eVaka, are less to install and keep in step.
- **The password in the config, as MyClub's links are.** Rejected: it is a password to an account with the Kids' personal data, so it gets the secret store's protection, as Wilma's and Eepos's do.

## Consequences

- The API is internal to eVaka's own frontend and unversioned, the repository changes every week, and a city can turn an endpoint off. When an answer isn't what eVaka gave before, the Source says eVaka "changed" on the Brief's coverage line, the rest of the Brief still goes out, and `doctor` says the same.
- A wrong email or password is answered HTTP 403 with the body `Forbidden` (apigw's `auth-weak-login.ts` catches the service's `Forbidden` and sends `sendStatus(403)`), and only that is taken as one. Any other answer, such as 429 for more than 20 sign-ins an hour, a 403 with another body, or a 200 without the session cookie, is taken as eVaka being unreachable or having changed, so a changed sign-in never tells the family their password is wrong. apigw answers a failure of its own service during sign-in with the same 403, so such a failure reads as a wrong password for that evening.
- A session lapses after 32 minutes idle and can't be refreshed, so each evening run signs in again. Some cities email the guardian about a sign-in from a new device: the device cookie eVaka sets on each sign-in (`__Host-evaka-device-user-…`, for 90 days) is kept between runs in an owner-only `evaka-devices.json` beside the state, and `setup evaka` and `doctor` keep it too.
- eVaka gives the reservation deadline only as the first Monday still open for reservations (`reservableRange.start`); each city closes them a set number of hours before it (`citizenReservationThresholdHours`). The collector's table has those hours as of 2ad3203f, so the deadline is right only while a city keeps them, and a city given by its host, not in the table, gets no deadline.
- A closed day is a public holiday (`holiday`) on which none of the guardian's children has reservable time. A unit's own closures outside public holidays, and holiday periods, aren't read yet.
- A Hosted Household's eVaka password is held on the maintainers' server as its Wilma password is, and SECURITY.md says so.
- The hosted Brief's last line doesn't name eVaka among the Sources the hosted version doesn't read: a Hosted Household can have it.
- Amended 2026-11-05 (#790): the hosted sign-up has an optional eVaka step on its MyClub page, beside Eepos's: the city, picked from the collector's cities or given by its host, and the guardian's email and password. The service checks it as `setup evaka` does, signing in, reading the children and matching them to the Kids by name, before anything is made, so a wrong password (weak-login's 403 `Forbidden`) is said at once and the link stays good. One city at sign-up; a second is added by a maintainer with `setup evaka`. Without Wilma, an eVaka sign-in is enough to sign up. The device cookie the check got is handed to the Household with the password, so its evening runs sign in as the device that was checked and a city that emails about new devices emails once. The setup page's step is #791.
