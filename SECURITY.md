# Security and privacy

Parent Recap runs on the Household's own Mac, or Windows PC ([On Windows](#on-windows)). The program reads each Source from that Mac, sends what it read to the model the Household chose, and emails the Brief from Parent Recap's own address, `brief@parentrecap.com`, through the maintainers' gateway (ADR 0032). A Household whose AI is its own Claude Code or Codex and that reads its Gmail may instead send the Brief from that Gmail, as an advanced setting (ADR 0034, [Delivering](#delivering)); otherwise the Household's Gmail, when it has one connected, is only read. The only Parent Recap server is the maintainers' gateway: every Household sends its Briefs through it unless it sends them from its own Gmail, and a Household that chose it as its AI sends its model calls there too. After each evening run the computer also sends it a Run Report, how the run ended in fixed words and numbers, unless the family turned that off; a Household that sends from its own Gmail sends none unless it turns it on (see [The maintainers' gateway](#the-maintainers-gateway) and [The Run Report](#the-run-report)). The same server also runs the program itself for a Household the maintainers host because it has no computer to run it on, and then keeps its Wilma login, MyClub links, config and Briefs (see [The hosted version](#the-hosted-version)). This page lists where data goes and where every secret lives, so you can decide before installing whether to trust it with your Household's messages.

## How data flows

Each evening the scheduled job on your Mac does the following. For a Hosted Household the same job runs on the maintainers' server instead, as the Household's own Linux user, and reads only Wilma and MyClub, and Eepos and eVaka when the family gave them at sign-up or the maintainers added them: its path is in [The hosted version](#the-hosted-version).

Before it reads anything, the evening run (and Weekend Picks) waits up to a minute for the network, as after the computer woke up: it opens a connection to port 443 of the AI's host (`api.anthropic.com` for Claude, `chatgpt.com` for ChatGPT, the gateway's host for the gateway) and closes it again, sending nothing over it.

### Summarizing

Everything read above for that evening goes to the model you chose, cut down first on your Mac as [What the AI sees](README.md#what-the-ai-sees) describes, and with it what the config says of each Kid: their name and aliases (as Kid A, Kid B while the AI filter is on, unless you ask for their names to go as they are), and their grade, class, school and activities when the config has them. It also gets the names of the WhatsApp groups you picked and which Kid each is for, the notices and action items of the last few Briefs (so it doesn't repeat them), and the Weekend Picks preferences you configured. In `google` calendar mode it also gets your calendar's events of the next 7 days (`google_calendar.lookahead_days_context`), which the program reads from Google Calendar for this, not only writes: only Kid-related events keep their title and place, and any other is sent as a busy time ([What the AI sees](docs/config.md#what-the-ai-sees)).

- **Claude** (`llm.backend: claude`): through the `claude` CLI to Anthropic, under your Claude subscription or API key. Each call runs in an empty temporary folder with no tools, no MCP servers and none of your own Claude settings, so the model can't run commands or read files. The prompt goes to the CLI on standard input, not on its command line, so other accounts can't see it in the process list. The session isn't saved, so nothing is left under `~/.claude/projects`.
- **ChatGPT** (`llm.backend: codex`): through `codex exec` to OpenAI, under your ChatGPT account. Each call runs in an empty temporary folder with a read-only sandbox, with Codex's shell, command execution, apps and plugins turned off, so the model can't run commands or read files. The prompt goes on standard input, the session isn't saved, and your own Codex configuration and MCP tools aren't loaded.
- **Parent Recap's gateway** (`llm.backend: gateway`, invited Households only): the program itself sends each call over HTTPS to the maintainers' gateway, with your Gateway Key, and the gateway passes it on to Anthropic under the maintainers' account. Neither Claude Code nor Codex runs. See [The maintainers' gateway](#the-maintainers-gateway).

How long Anthropic or OpenAI keep that data, and whether they train on it, is set by your account with them, not by Parent Recap. On consumer plans both may train on your chats by default, and the setup page says where to turn that off. Through the gateway, the account is the maintainers' Anthropic API account, under Anthropic's [Commercial Terms](https://www.anthropic.com/legal/commercial-terms) (section B: "Anthropic may not train models on Customer Content from Services"; [Anthropic's privacy centre](https://privacy.claude.com/en/articles/7996868-is-my-data-used-for-model-training) says the same of its API), which don't let Anthropic train its models on what is sent.

The chat skills (`/parent-recap:setup` and `/parent-recap:manage` in Claude Code, `$parent-recap-setup` and `$parent-recap-manage` in Codex) run in your own Claude Code or Codex like any other chat, with their tools on, so what they read goes to Anthropic or OpenAI under your account. To check how Parent Recap is running, `manage` has the AI run `parent-recap doctor`, whose results name what [the Problem Report](#the-problem-report) lists, and read the last lines of the logs; to change a setting it reads and edits `~/.family/config.yaml`, all but its MyClub links. It never prints a message's text or runs `parent-recap collect`, but those results, log lines and the config reach your AI provider.

### The maintainers' gateway

Every Household has a Gateway Key to the gateway the maintainers run: every Brief is sent through it (ADR 0032). A Household whose AI is its own Claude Code or Codex gets a key for sending only from the gateway itself, bound to its Recipients, each of whom confirms their address by email before the gateway sends them anything (ADR 0033); an invited Household without a Claude or ChatGPT subscription can have the gateway write the Brief too, with the maintainers paying for its model calls, and gets that key from the maintainers (ADR 0014). A Household should know what that means before installing. Its deployment config is public in [`ops/gateway/`](ops/gateway/README.md) (ADR 0015).

- **What passes through it:** for a Household that has it write the Brief, every model call of the evening Brief, its translations and Weekend Picks, as described above, so after the AI filter when it's on: the messages' text, with your Kids as Kid A, Kid B and other people's names, phone numbers, email addresses and links as placeholders. Also your Gateway Key, in each call's `x-api-key` header, and the small test calls setup and `doctor` make. Every Household, whatever its AI, sends it each Brief, Weekend Picks and first Brief from setup as the Recipients read them, unless it sends them from its own Gmail (ADR 0034), with the Recipients' addresses and the `.ics` attachment, and the Gateway Key they're sent with; see [Delivering](#delivering). After each evening run, its Run Report, unless turned off; see [The Run Report](#the-run-report). A Problem Report only when you answer yes in Parent Recap Check; see [The Problem Report](#the-problem-report). Nothing else of your Household, such as your passwords or your config, is sent to it.
- **What it keeps of a key for sending only (ADR 0033):** the key, and the Recipients' addresses bound to it, each with its language and whether and when it was confirmed, so that the gateway sends only to them. Nothing else of your Household. When the program asks for such a key, or binds changed Recipients, it sends the gateway the Recipients' addresses and languages, and the gateway emails each of them a confirmation link from `brief@parentrecap.com`. To rate-limit these requests it counts them for a day by a one-way hash of the caller's IP address and of each address, and keeps no IP address.
- **What it keeps:** for each call, the Gateway Key it came with, the model, the number of tokens, the cost, the HTTP status and the time, for 90 days. It doesn't keep the request or reply text: content logging is off, and a request can't turn it on. Of a Brief it sends it keeps nothing: one log line with the key's name, the number of Recipients, the size and the outcome, never the subject, the text, the attachments or the addresses, and a count of the key's sends that day. Its web server keeps no access log. Its database holds each Gateway Key, which the maintainers' admin login can read, under a neutral label; which Household holds which key is known only to the maintainers.
- **Where it runs:** on an Oracle Cloud virtual machine in Stockholm, Sweden (EU), running the open-source [Bifrost](https://github.com/maximhq/bifrost) gateway (ADR 0016) behind the Caddy web server. Only its `/v1/messages`, `/v1/brief`, `/v1/report` and `/v1/problem` addresses (with `/v1/brief/key` and `/v1/brief/recipients`, which make and bind keys for sending only, the Brief's stop page and confirmation page, and the hosted version's sign-up page) are reachable from the internet, over HTTPS; its admin interface is reachable only from the server itself. From there each call goes to Anthropic's API, and each Brief to OCI Email Delivery in the same Oracle Cloud region, which keeps no message content, only bounces, complaints and delivery counts.
- **What the maintainers can do with a key:** each key is capped at $0.10 a day and at 4 Briefs sent a day, and the maintainers can turn it off at any time. A call past the cap or with a turned-off key fails, and that evening's Brief says its Digest couldn't be written. A send past the cap or with a turned-off key fails too: no Brief goes out that evening, the log says why, and the night's messages come in the next Brief.

Switching to Claude or ChatGPT with `manage` stops the model calls to the gateway from the next Brief on; the Brief is still sent through it. Uninstall removes the Gateway Key from the Keychain. To have a key turned off, ask the maintainers who sent it.

### Delivering

- For every Household (ADR 0028, ADR 0032), the program posts each Brief, Weekend Picks and the first Brief from setup, with its Recipients' addresses and attachment, over HTTPS to the maintainers' gateway with your Gateway Key, and the gateway hands it to OCI Email Delivery, which sends it from `brief@parentrecap.com`. Neither keeps the message (see [The maintainers' gateway](#the-maintainers-gateway)). New calendar events go with it as an `.ics` attachment. Nobody reads that address: the Brief says so and names the setup parent's address to write to instead. Unless you turn on sending from your own Gmail (next item), your Gmail and its App Password are never used to send; they're needed only if the Gmail Source reads your mail. Without a Gateway Key no Brief can be sent: a Household whose AI is its own Claude Code or Codex gets one for sending from the gateway (ADR 0033), and the Brief goes only to the Recipients who confirmed their address through the link in the gateway's email; `doctor`, the setup page and the evening run's log say whom the email went to. A Household whose AI is the gateway asks the Parent Recap team for its key.
- Sending from your own Gmail (ADR 0034), an advanced setting a Household whose AI is its own Claude Code or Codex and that reads its Gmail with an App Password can turn on from the setup page's Finish or with `manage` (never asked during setup): the program sends each Brief, Weekend Picks and the first Brief from setup from that Gmail address over SMTP to `smtp.gmail.com` (port 465, encrypted from the first byte), signed in with the same App Password it reads with. The gateway then sees none of them, and nothing goes to it unless you turn the Run Report on ([The Run Report](#the-run-report)) or send a Problem Report ([The Problem Report](#the-problem-report)). The computer still reaches your own AI provider (Anthropic or OpenAI), Gmail and the Sources; Linked Events, for Weekend Picks; Google Calendar, in `google` calendar mode; and GitHub each evening for `release.json`, and for an update the hosts in [How Parent Recap updates itself](#how-parent-recap-updates-itself). None of these requests carries the Household's messages except those to the AI provider and to Google. No Gateway Key is asked for and the Recipients confirm nothing; a key stored before stays in the Keychain, unused, so switching back needs no new confirmation. Replies reach you, each Brief stays in that Gmail's Sent folder, and the maintainers don't see these Briefs or count them. If Google stops accepting the App Password, both reading that Gmail and sending the Brief stop until a new one is stored; `doctor` says so. With the gateway as the AI the setting doesn't apply: the Brief's messages already go through the gateway to be written.
- In Google Calendar mode, new events are written to your calendar through the Google Calendar API instead.

### The Run Report

After each evening run, the program sends the maintainers' gateway its Run Report (ADR 0048), so that when a Brief is late or missing the maintainers can see why without asking you for logs or screenshots.

- **What it holds:** only the fields the program names in one list (`FIELDS` in `app/src/family_brief/last_run.py`): Parent Recap's version, the system and its version, when the run ended and how it was started, its exit code, duration and peak memory, what each Source read (a count) or why it failed (a fixed key such as `wilma-egress`), the AI's result, the Brief's outcome (sent, nothing to tell, or failed with a fixed key), how the program's last update went (`none`, `updated`, `failed`, `switched-back` or `waiting-for-family`; see [How Parent Recap updates itself](#how-parent-recap-updates-itself)), and for an error that stopped the run its type and the line of Parent Recap's own code, never its message. No message text, name, address, subject or path. The gateway refuses a report with any other field or value.
- **What leaves is the file you can read:** the run writes it to `~/.family/last-run.json`, and the copy that is sent waits in `~/.family/run-reports/` until the gateway takes it, byte for byte the same.
- **How it is sent:** from inside the program, over HTTPS to `/v1/report` on the same gateway address the Brief goes to, with your Gateway Key in the `x-api-key` header. A Household without a Gateway Key, as one that sends from its own Gmail can be, or whose key the gateway no longer knows, sends it under a random id its program makes once and keeps in `~/.family/run-reports/id`, which names nobody. No shell, PowerShell or `curl` runs. The program reads nothing of the gateway's answer but whether the report was taken.
- **When it can't be sent:** a run with no network, or one whose report the gateway didn't take, sends it with the next run's; one not sent within a week is dropped. Sending comes after the Brief and never stops or delays it.
- **What the gateway keeps:** each report, with when it came, under its Gateway Key or its id, for 30 days, then it is deleted. Reports without a key are rate-limited by a one-way hash of the caller's IP address, which isn't kept with the report. The maintainers see from them which Households run Parent Recap, on which version, and whether each evening's Brief went out.
- **When it is on:** by default for a Household that sends its Brief through the gateway, new or already installed; off for one that sends from its own Gmail (ADR 0034), until the family turns it on: turning own-Gmail sending on, the setup page asks whether to send it too, and sends nothing until they say yes. Turn it off or on with the switch under "Later, if you need it" on the setup page's Finish, by asking in the chat (`manage`), or with `run_report.enabled: false` or `true` in `~/.family/config.yaml` ([config](docs/config.md)); once set, it stays as set whichever way the Brief is sent. `parent-recap doctor` says whether it is on and when the last one was sent. A Hosted Household sends none: its status is read on the server.

### The Problem Report

When something is wrong and you want the maintainers' help, Parent Recap Check can send them a Problem Report (ADR 0048, #925). It is sent only by your own yes, each time: nothing sends one in the background, and nothing else asks.

- **What it holds:** `doctor`'s results as the window shows them, Parent Recap's version, the system and its version, the last lines of Parent Recap's own logs (the evening run's, the update's and the newest install's), and the one line you write, if you write one. `doctor`'s results name, for each thing it checks: your config's path and the Recipients' addresses; the Gmail address it reads (or sends from); the Kids as Wilma lists them, and each Wilma username with its school's Wilma; the names of the picked WhatsApp groups; the addresses new Google Calendar events invite; the usernames, and the Kids' names as each lists them, of Eepos, eVaka, Social Schools and Konnect; which Kid each MyClub link is for (never the link); and the Local Files folder. A check that fails adds the error it got word for word, which can quote any of these, or a line of a config it couldn't read. `doctor` prints no password, key or message text itself. Of the logs only lines Parent Recap itself wrote with their time first go; pip's or an installer's output and error tracebacks are left out. Those lines can still hold free text: a Gmail search with a sender's address, a Kid's name, a Source's username and school or server when its sign-in failed, the titles of calendar events written, moved or skipped, or the address of a Recipient who hasn't confirmed it yet. So a person on the team may read all of this.
- **When it is sent:** Parent Recap Check runs `doctor --offer-problem-report`. After the checks, the window shows the whole report and asks once, in your family's language, whether to send it. Only a yes and Return sends it: in English `yes` or `y`; in Finnish `kyllä`, `kylla` or `k`; in Chinese `是` or `是的`; in Finnish and Chinese `yes` and `y` too, whatever the case and with spaces around it; no, an empty answer, any other answer or closing the window sends nothing, and nothing is kept to send later. `parent-recap doctor` run any other way, in Terminal, by the setup page or by your AI in a chat, never asks and never sends.
- **How it is sent:** from inside the program, over HTTPS to `/v1/problem` on the gateway address the Brief goes to, with your Gateway Key, or without one, as after an install that didn't finish, under the Run Report's random id (`~/.family/run-reports/id`) or a new random id when there is no config yet. No shell, PowerShell or `curl` runs.
- **What the gateway keeps:** each report as it came, with when it came and under which key or id, for 30 days, then it is deleted. It takes at most 64 KB a report and a few a day from one key or one caller, and refuses the rest. Its log says only that a report came, from which key or id and how large it was, never what it says. The maintainers read it on the server and don't paste it elsewhere ([ops/gateway/README.md](ops/gateway/README.md#problem-reports)).

### What stays on the Mac

- `~/.family/config.yaml`: your configuration, including Kids' names, allowlisted senders, chosen WhatsApp chats and MyClub links. Setup creates it owner-only (`chmod 600`), inside `~/.family`, which the installer makes owner-only (`chmod 700`).
- `~/.family/state.json`: which messages and events were already handled, and when a Brief last went out to each Recipient's address.
- `~/.family/last-run.json`: the Run Report, how the last evening run ended, in fixed words and numbers only: the version and system, when it ended and how it was started, its exit code, duration and peak memory, what each Source read or why it failed by a fixed key, the AI's result, the Brief's outcome, how the last update went by a fixed word, and an error's type and line in Parent Recap's code, never its message (ADR 0048). Unless it is turned off, a copy goes to the maintainers' gateway after each run, waiting in `~/.family/run-reports/` until it is taken ([The Run Report](#the-run-report)).
- `~/ParentRecap/`: every Brief as Markdown, plus the raw messages it was built from (`*.raw.json`), Weekend Picks under `weekend_events/`, logs and model diagnostics under `~/ParentRecap/logs/`, and `held-back-list.txt`, the list of held-back messages that `parent-recap ai-filter-report --held-back` opens in TextEdit. These are not encrypted beyond your Mac's own disk encryption.

Everything Parent Recap writes is owner-only: files `600`, folders `700`, so other accounts on the same Mac, such as a Kid's own account, can't read them. The installer makes `~/ParentRecap` owner-only, the program and its scheduled jobs create files with umask `077`, and each run takes group and other access off the archive, log, Weekend Picks and `~/.family` folders and the files in them (such as config backups), which also fixes installs from before 0.4.0.

### What the install puts on the computer

Everything an install puts on the computer is either inside the release or checked against a checksum the release holds: the Python and Node the program runs on against the SHA-256 checksums pinned in `install.sh`, `install.ps1` and `app/windows_install.py`, the Linked Device's npm packages and, for a Household that connected Wilma, the wilma CLI with every package it needs, each against the lockfile shipped for it (`npm ci`, with package scripts off), and the Python packages, pip included, against the checksums in `app/constraints.txt` (pip's `--require-hashes`). A package file that doesn't match, or a package the file doesn't pin, stops the install, and the version already installed keeps running. A wilma CLI installed before the release had that lockfile was pinned by its version only (ADR 0008): it stays as it is while the release pins the same version, and the checked tree takes its place when the pinned version next changes.

### The setup page

`parent-recap setup page` serves the setup page from the Mac itself, only while setup needs it. It listens on 127.0.0.1, so no other computer can reach it, on a free port. Its address carries a one-time random code that every request must have, except the browser's own request for its tab icon, which gets an empty answer, and it refuses a request whose Host or Origin isn't its own address, so a website open in the browser can't use it. It serves only the program's own page files, which load nothing from the internet, and it logs nothing about requests. It stops after 30 minutes without a request.

The page's buttons that open a website open it in your own browser, which then talks to that site as it would for any link. The one for Google's App Passwords page carries your Gmail address in the link (`myaccount.google.com/apppasswords?authuser=<address>`), so Google opens it in that account rather than the browser's default one. When your AI is Claude, the page installs or updates the Parent Recap plugin in Claude Code, and Claude Code downloads it from this repository on GitHub (`kinlace/parent-recap`, the `stable` branch), as `claude plugin marketplace add` does.

To build the check page, it reads only the senders of the last 60 days of Gmail (their domains and one sender name each), never the mail, and keeps them in setup's progress, `~/.family/setup-progress.json`, which is owner-only. It never offers a public mail service such as gmail.com for the allowlist, so private mail isn't read. The health check it runs, and the checks Finish shows, return each check's name and status to the page, with what it is about where `doctor` says (a language, a Kid's MyClub, a school, a city or a portal) and the groups it concerns, such as the addresses of Recipients who haven't confirmed theirs yet; for a check that isn't OK also why, by a fixed key, and `doctor`'s detail, which can quote an address or an error and which the page folds under "Details for the Parent Recap team" for the family to copy if they want (#500). An OK check's detail stays out. The page is on the Mac, so none of this leaves it unless the family copies it somewhere.

For the first Brief, it makes the real Brief through a `bg` job, as `parent-recap run --preview` does, which sends nothing and writes no archive or state, only one line in the evening job's log with counts: each Source's messages, the held-back ones, and the Digest's length and its Notices, Action Items and new events, with no message text, names or subjects. The Brief stays in Parent Recap's memory and is shown in a sandboxed frame on the page that runs no scripts and opens no links. "Send it to me" emails it to the setup parent only, the first Recipient, and records only that it reached them.

At Finish, it installs the evening job and the Mac's wake-up as `parent-recap schedule install` does. The Mac password goes into macOS's own administrator dialog, never the page, and the page has no field for it. Another repeating wake schedule on the Mac is replaced only once the parent presses Replace it. It then checks the outcomes as `parent-recap setup status` does and returns only each outcome and whether it's true, never the reasons, which can name an address. Once every outcome is true, the server stops.

### Where MyClub links can appear

A MyClub calendar link carries a personal token that lets anyone read the Kid's club calendar. The parent pastes it into a macOS dialog with hidden input (`parent-recap setup myclub`), into the setup page's own password field (ADR 0007), or into their own Terminal with the older `scripts/setup_myclub.py`, never into the Claude or Codex chat, and it's kept only in `~/.family/config.yaml` and the config backups next to it in `~/.family`. Each night it's sent to MyClub to download the calendar. When the download fails, `doctor`, the logs, the archive and the Brief name only the MyClub server and the HTTP status, never the link's path or token.

## How Parent Recap updates itself

On a Mac and on a Windows PC, Parent Recap installs new releases by itself after the evening Brief (ADR 0047, ADR 0052), those that change something the Household uses (ADR 0051). A program that downloads and runs code in the background deserves a close read, so this section says what the update asks for, what it runs, what it writes and what it never does. [`app/src/family_brief/update.py`](app/src/family_brief/update.py) starts with the same statements, and the tests in `app/tests` show them. For a Hosted Household, and on a PC without Windows' own `ssh-keygen`, the program doesn't update itself: none of this runs there. What differs on Windows is in [On Windows](#on-windows) below. How it looks to a family, and how to turn it off, is in [Updating](docs/install.md#updating).

A Household that set up after this shipped saw it on the setup page, by the switch that turns it off. A Household installed before learns of it from the first Brief after an update, which says that Parent Recap now updates itself and where to turn that off.

### What the update asks for, and from where

The update's own requests go to this repository on GitHub, `kinlace/parent-recap`, and nowhere else. The repository and the host names are constants in the program, so nothing read from the network changes where it downloads from:

| Host                                                                    | What is asked                                                                                                                                       |
| ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `raw.githubusercontent.com`                                             | `release.json` on the `stable` branch: the version it holds and the last version that changed each part, once each evening after the Brief, and once when the family adds a Source whose code is in a folder of its own |
| `github.com`                                                            | A newer release's zip and its signature, `releases/download/v<version>/parent-recap-<version>.zip` and `.zip.sig`                                   |
| `objects.githubusercontent.com`, `release-assets.githubusercontent.com` | The same two files, where GitHub redirects their download. A redirect to any other host, or to an address that isn't HTTPS, is refused, not followed |

Each request is a plain GET over HTTPS with nothing about the Household in it: no cookie, no sign-in, no name or address, no version of its own, and no proxy or `.netrc` setting from the computer. Its `User-Agent` is `parent-recap-update`. GitHub sees the computer's IP address, as it does for any download.

### What is verified, and what runs

- The zip is checked against its signature and the two public keys the installed program holds ([Release signatures](#release-signatures)) before anything in it is used. A zip that doesn't verify is deleted, and its installer never starts.
- The `release.json` that `stable` holds isn't signed, so after verifying the zip the program reads the version inside it: it must be the one asked for and higher than the installed one. An older signed zip in a newer release's place is refused.
- A release that changes nothing the Household uses isn't installed, and nothing of it is downloaded (ADR 0051). `release.json` on `stable` says, for the core and for each Source whose code is in a folder of its own, the last version that changed it. The program installs the release only when the core, or a Source the Household has connected, changed in a version newer than the installed one; a Source without a folder of its own counts as the core. Where the file doesn't say (it has no `parts`, or lacks the core or a connected Source), or the Household's config can't be read, the release is installed. A file that can't be read ends that evening's look with nothing installed, and the next evening looks again. Since the file isn't signed, a false one could make a Mac skip a release, as holding `stable` back could, or download one, whose signature is then checked as above.
- A Household that skipped releases may hold an old copy of a Source it never connected. So when the family adds a Source whose code is in a folder of its own, on the setup page or with its `setup` step in Terminal, the program first reads `release.json` on `stable`, that one request, before anything they typed goes to the Source. When the Source's part changed in a version newer than the installed one, it installs the newest release as an update the family started, downloaded and verified as above, and the step goes on in the new version: Terminal's step is run again by it, and the setup page's program is started again by it on the same local port with the same one-time code. When the file can't be read or the update can't be done, the step says so and nothing is sent to the Source or saved. Where the program doesn't update itself (the hosted version, a PC without `ssh-keygen`), the step asks no host and goes on.
- Whether a release needs the family at the computer is read from `release.json` inside the verified zip, and nowhere else.
- Nothing is piped from the network into a shell. The program downloads and unpacks the zip itself, without `curl`, `unzip` or a shell.
- What runs is the verified release's own installer: on a Mac its `install.sh`, run as a file with `/bin/bash`, so a shell does run a script during an update, but only one the signature covers; on Windows its `app\windows_install.py`, run as a file with the installed version's Python, so no `.ps1` file runs (see [On Windows](#on-windows) for the one PowerShell command it starts).
- Then the new version's `parent-recap doctor` runs, as the installed version's did before the install, each with every check `doctor` makes, the requests it sends included ([What it never does](#what-it-never-does)). A check it fails that the version before passed switches back to that version. So does an installer that didn't finish once it had switched (a non-zero exit status, or ended at its time limit), and a `doctor` that didn't run or crashed.

### What the installer fetches

The verified installer (`install.sh` on a Mac, `app\windows_install.py` on Windows) makes requests of its own, to the hosts any install uses. Each fetch happens only when the release needs it:

| What                                                                                        | From                                                                                                  | How it is checked                                                                                                                         |
| ------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| The Python packages, pip included (Google's too, for a Household that uses Google Calendar) | PyPI: `pypi.org`, `files.pythonhosted.org`                                                            | By checksum: each against the SHA-256 checksums in the release's `app/constraints.txt` (pip's `--require-hashes`) |
| The Linked Device's npm tree                                                                | `registry.npmjs.org`                                                                                  | By checksum: against the lockfile in the release (`npm ci`, with package scripts off)                                                     |
| A new Python, when the release pins another one                                             | `releases.astral.sh`, or else `github.com` (astral-sh/python-build-standalone) and where it redirects | By checksum: the SHA-256 pinned in the release's `install.sh` (on Windows, its `app\windows_install.py`)                                    |
| A new Node, when the release pins another one                                               | `nodejs.org`                                                                                          | By checksum: the SHA-256 pinned in the release's `install.sh` (on Windows, its `app\windows_install.py`)                                    |
| The wilma CLI, where it is installed (a Household that connected Wilma), when the release pins another version | `registry.npmjs.org`                                                                                  | By checksum: the CLI and every package it needs against the lockfile in the release (`npm ci`, with package scripts off)                  |

So the signature covers everything an update installs, the wilma CLI and its packages too. A Python, a Node or a Python package that doesn't match its checksum, or a Python package the release doesn't pin, stops the install before the switch, and the version already installed keeps running ([What the install puts on the computer](#what-the-install-puts-on-the-computer)). The npm tree and the wilma CLI are fetched after the switch: one that fails, as on a package that doesn't match the lockfile, leaves the tree or the CLI already there, the new version runs with it, and the next install tries again.

### Where an update writes

An update writes where an install already writes, and nowhere else. On a Mac:

- In Parent Recap's folder, `~/ParentRecap`: `update/` (its state, `state.json`, and the download's folder, removed when the update ends), `plugin/` (the release), `versions/` and the `app` link (the new version beside the one before), `runtime/` (a new Python or Node), `baileys/`, `wilma/`, `bin/` and `logs/` (`update.log`, and the install's log).
- In `~/.family`: `install-record.json`, setup's record of what the install put on the Mac. An update the family started holds `run.lock`, the evening run's lock, for as long as it runs, so no Brief is made and no other update runs beside it; it makes that empty file if it isn't there. Such an update, which installs the evening jobs again, also takes group and other access off Parent Recap's files, as every run does.
- The marked line in `~/.zprofile` that puts `parent-recap` on the PATH.
- `~/Applications/Parent Recap Settings.app` and `~/Applications/Parent Recap Check.app`.
- The evening jobs' files in `~/Library/LaunchAgents` (`com.parentrecap.*`), written again only when a job's definition changed or the job isn't loaded. The evening's own update leaves them as they are.
- The Mac's wake schedule (`pmset repeat`), only when the family started a release that needs them and an older version's wake has to move: macOS then asks for the Mac password in its administrator dialog. Never in the background.
- For a Household with a Wilma sign-in, the wilma CLI's `~/.config/wilmai/config.json` and the Keychain items it keeps its passwords in.
- For a Household that uses Codex, the two skills in `~/.agents/skills`, `parent-recap-setup` and `parent-recap-manage`.
- pip's cache, `~/Library/Caches/pip`. The downloads of a new Python or Node and npm's cache go in temporary folders that are removed.

On Windows the places are those of [On Windows](#on-windows) below.

It doesn't change the config, the Keychain items or Credential Manager credentials Parent Recap stored, the Linked Device's pairing or the archive of Briefs. [docs/setup-internals.md](docs/setup-internals.md#how-an-update-works) says what each step writes.

### What it never does

- The update code never starts the wake's password dialog in the background. Moving an older version's wake is the step of an install that asks for the Mac password, and an install that runs for an update skips it (`PARENT_RECAP_UPDATING`, which `family_brief/schedule_update.py` reads), unless the family started a release that needs them. That is the one dialog the code stops. A release that would open any other dialog (a new permission, a QR scan, another password) is marked as needing the family when it is cut, in `release.json`, which the release steps require ([CONTRIBUTING.md](CONTRIBUTING.md#releasing), "A release that needs the family"). A release marked so isn't installed by itself: it waits for the family to start it, and only then does its installer run with its dialogs. So that nothing else opens a dialog in the background is a rule of how the maintainers cut releases, not something the program checks.
- It adds no background item. The evening jobs start the program from one path that stays the same across versions, so an update leaves them as they are and macOS has nothing new to announce.
- It reads nothing the maintainers' gateway answers. Nothing the gateway says can start an update or choose what a Household gets: every Household takes the same release from the same public address.
- It sends the maintainers nothing of its own. The update's own code makes no request to the gateway. But each update that installs a release runs the full `parent-recap doctor` twice, the installed version's before and the new one's after, and `doctor` makes the requests it makes when you run it: it signs in to each Source and Gmail, makes a small test call to your AI, reads Google Calendar in `google` mode and checks Linked Events is reachable. For a Household that sends its Brief through the gateway, each `doctor` also sends the gateway the Gateway Key with one Brief request it refuses, so nothing is sent, and the Recipients' addresses and languages, to ask who has confirmed (`/v1/brief` and `/v1/brief/recipients`); with the gateway as its AI the test call goes there too, with the key. A Household that has no Gateway Key yet but may have one is given one then, and the gateway emails its Recipients the confirmation link, as an evening run does ([The maintainers' gateway](#the-maintainers-gateway)). Of what `doctor` printed the update keeps only which checks failed, by their names, in its log; a check's name can hold what it is about, such as the Kid of a MyClub link. The details of an update stay in the computer's own update log (`~/ParentRecap/logs/update.log`, on Windows `%LOCALAPPDATA%\ParentRecap\logs\update.log`), which names versions and steps and nothing of the family's messages. The [Run Report](#the-run-report), when it is on, says how the last update went in one fixed word: `none` (the program doesn't update itself here, as for a Hosted Household or a PC without `ssh-keygen`, or hasn't tried a release yet), `updated`, `failed`, `switched-back`, or `waiting-for-family` (a release that needs the family waits for them to start it). It is written before the evening's own update, so it says how the update before went. Nothing the gateway answers to it is read by the update.
- It never installs a version that isn't higher than the one installed.
- It never starts by itself outside the evening run: a Brief started by hand, a preview and Weekend Picks don't update.

### With the switch off

The switch on the setup page, or `parent-recap update off`, turns updating off (the config's `updates.enabled`). Parent Recap then still asks `raw.githubusercontent.com` once each evening for `release.json` on `stable`, that one request and no other, so the Brief can say once that a newer release is out, when that release changes something the Household uses. It downloads nothing: no zip and no signature. `parent-recap update` and **Update now** on the setup page still install the newest release when the family asks.

### The install line

The signature protects updates. The first install, and a reinstall with the install line, check no signature: they trust GitHub over HTTPS, and the maintainers' accounts there. A check inside `get.sh` wouldn't change that, since it would come from the same place as `get.sh`. The line in the README fetches `get.sh` from the `stable` branch over HTTPS and runs it in a shell, and `get.sh` downloads the `stable` branch and runs its `install.sh`. Whoever would rather check one downloads the release zip, verifies it by hand as [Release signatures](#release-signatures) says, and installs from the package file ([Other ways to install](docs/install.md#other-ways-to-install)).

## Release signatures

Every release zip on the [Releases page](https://github.com/kinlace/parent-recap/releases) has an OpenSSH signature beside it, `parent-recap-<version>.zip.sig`, made with `ssh-keygen -Y sign` under the namespace `release@parentrecap.com`, so a signature one of the keys made for anything else is never a release's (ADR 0047). The program ships the two public keys a release may be signed with, in [`app/src/family_brief/release_signers`](app/src/family_brief/release_signers), and checks a zip against them with the system's own `ssh-keygen` by its full path, `/usr/bin/ssh-keygen` on a Mac and `%SystemRoot%\System32\OpenSSH\ssh-keygen.exe` on Windows (`family_brief/release_signature.py`, #953), so verifying installs nothing. A PC without Windows' OpenSSH client can't verify a release, and the program tells that apart from a signature that doesn't verify:

- **`workflow`** is the release workflow's key. It is the secret `RELEASE_SIGNING_KEY` of the GitHub environment `release-signing`, which only `v*` tags may use; only the step that signs is given it, in a job that can read the repository and nothing more. The workflow checks the signature against this key before it publishes the release or moves `stable`.
- **`backup`** is held by a maintainer outside GitHub. It signs a release by hand when the workflow's key is lost or leaked, so a new workflow key can reach installed programs in a release they already trust ([CONTRIBUTING.md](CONTRIBUTING.md#releasing)).

A signature says a zip is one of ours, not which release it is. To check one yourself: `ssh-keygen -Y verify -f app/src/family_brief/release_signers -I workflow -n release@parentrecap.com -s parent-recap-<version>.zip.sig < parent-recap-<version>.zip` (`-I backup` for one the backup signed). On Windows, in PowerShell, which has no `<`: `cmd /c "%SystemRoot%\System32\OpenSSH\ssh-keygen.exe -Y verify -f app\src\family_brief\release_signers -I workflow -n release@parentrecap.com -s parent-recap-<version>.zip.sig < parent-recap-<version>.zip"`.

## On Windows

On a Windows 11 PC ([Parent Recap on Windows](docs/windows.md), ADR 0019) data flows as above, and the setup page works the same way. What differs is where things are kept and who on the PC can read them.

- **The secrets** (the Gmail App Password, the Gateway Key, the Claude token and the Eepos, eVaka, Social Schools and Konnect passwords) go into Credential Manager, one generic credential each, named `Parent Recap/<account>` with the accounts above, and the wilma CLI puts the Wilma password there too, under `ai.wilm.wilma-cli` (Control Panel → Credential Manager → Windows Credentials). They're kept on this PC for this Windows user and never roam to another PC. Parent Recap writes and reads them through Windows' own Credential Manager functions, never on a command line, and the setup page takes them in its own fields as on a Mac.
- **Any program you run as the same Windows user can read them without asking.** Windows has no counterpart to the Keychain's per-program trust (ADR 0009): a program you run under that account, including one you shouldn't have trusted, gets the Gmail App Password, the Gateway Key, the Claude token and the Wilma password (ADR 0021).
- **The files** are in `%LOCALAPPDATA%\ParentRecap` (the program's versions, its own Python and Node, the wilma CLI, the install's and the update's logs), `%USERPROFILE%\ParentRecap` (the archive, the evening run's logs), `%USERPROFILE%\.family` (the config and state), `%USERPROFILE%\.config\wilmai` (the wilma CLI's sign-ins, their passwords in Credential Manager once the CLI has moved them, **not encrypted** as above until then) and Codex's `%USERPROFILE%\.codex`. The owner-only permissions above don't apply on Windows, where Python can set only a file's read-only flag ([Python's `os.chmod`](https://docs.python.org/3/library/os.html#os.chmod)). Parent Recap sets no permissions of its own there, so who else on the PC can read these folders is whatever Windows allows for the rest of your user folder.
- **The evening run** is a Task Scheduler task that runs as you, only while you're signed in (ADR 0021). Setup never asks for your Windows password, stores none, and needs no administrator rights.
- **The install line** runs `install.ps1` from the `stable` branch, which isn't signed yet. It checks the Python it downloads against the SHA-256 checksum pinned in it, then hands over to the release's `app\windows_install.py`, which checks the Node against the checksum pinned there, and the Python packages against the checksums in `app\constraints.txt`, as on a Mac ([What the install puts on the computer](#what-the-install-puts-on-the-computer)). On the setup page, ChatGPT's Codex CLI is installed with OpenAI's own installer, and Claude Code with Anthropic's.
- **The update** ([How Parent Recap updates itself](#how-parent-recap-updates-itself), ADR 0052) asks the same hosts as on a Mac, with the same requests, and its installer fetches what a Mac's does, from the same hosts and checked the same way: the Python and Node against the SHA-256 checksums pinned in `app\windows_install.py`, the Python packages against `app\constraints.txt`, the npm trees against their lockfiles. It checks the release's signature with Windows' own `ssh-keygen`, by its full path, `%SystemRoot%\System32\OpenSSH\ssh-keygen.exe`, which only an administrator can replace, not with one the PATH finds.
- **No `.ps1` file.** What runs is the verified release's `app\windows_install.py`, run as a file with the Python of the installed version, without a console window. The update runs no `.ps1` file, so there is no execution policy for it to go round: the only PowerShell it starts is a hidden `powershell.exe -NoLogo -NoProfile -NonInteractive -Command` with a command fixed in the program, which writes the Start menu shortcuts (`family_brief/system/entries_windows.py`), as every install does. `install.ps1` is run only by the line a family pastes.
- **No administrator rights.** The update runs as you, from the evening task or from the command you type, and writes only to folders your Windows user owns. `app` is a junction, which needs no administrator and no Developer Mode.
- **Where it writes.** Where the install line writes, and nowhere else. In `%LOCALAPPDATA%\ParentRecap`: `update\` (its state, `state.json`, and the download's folder, removed when the update ends), `plugin\` (the release), `versions\` and the `app` junction (the new version beside the one before), `runtime\` (a new Python or Node), `baileys\`, `wilma\`, `bin\` and `logs\` (`update.log`, and the install's log). Outside it: setup's record, `%USERPROFILE%\.family\install-record.json`, and, for an update the family started, the evening run's lock beside it, `run.lock`, made empty if it isn't there; the `ParentRecap\bin` entry in your PATH under `HKCU\Environment`; the shortcuts in the Start menu's `Parent Recap` folder; pip's cache, `%LOCALAPPDATA%\pip\Cache`; and the Task Scheduler tasks named `Parent Recap <job>`, which only a switch back in an update the family started writes again, as `parent-recap schedule install` would. The evening's update leaves them as they are: they start the program through `app`.
- **The switch.** Windows can't replace a junction in one step, so the switch and a switch back happen under the run lock, with the Linked Device's task stopped before them and started after.
- **A step Windows stops**, as a company's Defender rule may, leaves the installed version running and the tasks as they were, and `logs\update.log` names the step and Windows' error word for word, so a Problem Report can name the rule. `doctor`'s Updates line shows the same.
- **A PC without `ssh-keygen`** in `System32\OpenSSH` (someone removed Windows' OpenSSH client) can't check a release's signature, so it doesn't update itself and downloads nothing: `doctor` says so, and the family pastes the install line to update.
- **Uninstalling** removes the `Parent Recap/…` credentials from Credential Manager with the rest ([Uninstalling](docs/windows.md#uninstalling)). Delete the Gmail App Password in your Google account yourself.

## The hosted version

A Household with no computer to run Parent Recap on can ask the maintainers to host it (ADR 0029). Only Households the maintainers invite are hosted: they send an Invite Link, and the family signs up on its phone (ADR 0031). The program then runs for it on the gateway's server in Stockholm ([The maintainers' gateway](#the-maintainers-gateway)). That is a bigger step than the gateway: the gateway keeps nothing of a Household's messages, while for a Hosted Household the maintainers hold its Wilma login and its Briefs on a server they administer, and so process its Kids' school messages on its behalf under GDPR. A Household that would rather keep them at home runs the program on its own Mac or Windows PC instead.

### How data flows when hosted

- **Signing up.** On the sign-up page, over HTTPS, the family types its Wilma town and login, checks the Recipients the maintainers prefilled, and pastes each Kid's MyClub link or leaves it empty, and may give an Eepos and an eVaka login. The sign-up service signs in to Wilma with that login and reads the Kids before anything is made, downloads each MyClub link once to check it, and signs in once to Eepos and eVaka with theirs. Until the Household is made, the answers, the passwords among them, are kept only in the service's memory: after 30 minutes they can't be used and the family signs in again, and they're dropped at the next sign-up or when the service restarts. Then it makes the Household's own Linux user, mints its Gateway Key, writes the config, the sign-ins and the key in that user's home, installs the evening job, and has the first Brief made and sent. Meanwhile the page asks the service every few seconds which of these steps has ended; the service keeps only that and how the sign-up ended, nothing secret, in memory until the page has seen it, for a day at most. The service never logs a request's address or body: its log says, for each sign-up, the Household's label and evening time, or which step wasn't taken and why, never the password, a link or an address.
- **Each evening.** The evening job runs as the Household's Linux user, at its own time from 21:00, held to half a CPU core and 400 MB of memory. It runs the one copy of the program installed on the server for every Hosted Household, which only root can change; a new release the maintainers deploy runs for every Household from its next evening (ADR 0035). It reads Wilma and MyClub as in [Reading the Sources](#reading-the-sources). Its Wilma requests leave through Finland (below); the others leave from the server's address. Its model calls go through the gateway with its Gateway Key ([Summarizing](#summarizing)), and the gateway sends the Brief from `brief@parentrecap.com` ([Delivering](#delivering)), with new events as an `.ics` attachment.
- **Wilma's way out.** Some Wilmas, Helsinki's and Vantaa's among them, turn away requests from outside Finland, so the server's Wilma requests, the sign-up's sign-in check and each evening's, leave through a proxy on a maintainer's Mac at home in Finland, over the maintainers' private network (ADR 0046). The connection to Wilma is encrypted end to end, from the server to Wilma, so the Mac relays it without being able to read it: it sees which Wilma is contacted and when, never a password, a session or a message, nor for which Household. It passes only connections to Wilma's addresses (`*.inschool.fi`), and only from the server; it holds no Household's data, which stays on the server in Stockholm. Wilma sees every Hosted Household sign in from that one Finnish home address. When the Mac can't be reached, the server goes to Wilma direct, and a Wilma that turns that away is left out of the Brief, which says so.
- **Not read.** WhatsApp: the server holds no Linked Device, because its session reads all of a parent's chats and can send as them (ADR 0029). Gmail: the hosted version has no Gmail step, so it holds no App Password and reads no mail.

### What the maintainers hold, and for how long

For each Hosted Household, in the home of its Linux user `ph-…` (8 random hex digits, a label that names no one):

- its Wilma login and session, its MyClub links, its Eepos login when it has asked for Eepos, its eVaka login when it has asked for eVaka, and its Gateway Key, as in [Where each secret lives](#where-each-secret-lives);
- its config, `~/.family/config.yaml`: the Kids' names, schools and classes as Wilma lists them, the Recipients' addresses and languages, and the evening time, with `state.json` as on a Mac and `last-run.json`, the Run Report: when the last run ended and how, how long it took and its peak memory, each in fixed words and numbers (ADR 0048);
- its archive, `~/ParentRecap/`: every Brief, the Wilma and MyClub messages it was built from, and the logs, as in [What stays on the Mac](#what-stays-on-the-mac).

All of it is kept until the Household is removed; the archive isn't trimmed, and only `state.json` drops what it records after 45 days. A Household has no setup page or `manage`: to change a setting it asks the maintainers, who edit its config, and to leave it asks them to remove it. Removing it ([Remove a Household](ops/gateway/README.md#hosted-households)) turns off its evening jobs, revokes its Gateway Key and deletes its Linux user with its home, and so everything above. What stays are log lines with nothing of the family in them: the journal's lines naming its label, and the gateway's per-call token counts and cost.

Outside the homes, the sign-up service keeps each Household's label and evening time, and each Invite Link with its prefilled Recipients' addresses until a Household is made from it. A link that expires unused keeps them until a maintainer deletes it.

### Who can read it

- **The Household's own Linux user.** Everything above is owner-only, files `600` and folders `700`, in a home only that user can open, so another Household's user can't read it. The secrets, the Wilma password among them, are owner-only files, since a server has no Keychain (ADR 0030): they have the protection of a file only its owner can read, no more.
- **The sign-up service.** It may run, as any Hosted Household's user, only the commands it needs to make the Household, check its status and remove it, each with exactly its arguments ([`signup.sudoers`](ops/gateway/signup.sudoers)): the release's `install.sh`, and the Household's own `parent-recap` with `signup household`, `run --first-brief`, `signup health` and `schedule uninstall`. So even a compromised service can't read the files that hold a Household's Wilma password, MyClub links or Gateway Key. It could still rewrite a Household's config through `signup household`, its Recipients among them, and so have a first Brief, made from the last three days' messages, sent to an address of its choosing. Its status command prints each Household's last run and the statuses of `doctor`'s checks, never message text, subjects, addresses or names.
- **The maintainers who administer the server.** Root reads every Hosted Household's files, secrets included. The server's disk is encrypted only as Oracle encrypts its volumes, so it doesn't keep the data from Oracle as the host. The maintainers' AI assistant has a login on the server that reads logs and service status, but has no sudo and can't open a Household's home.
- **No one else.** The setup in [`ops/gateway/`](ops/gateway/README.md) makes no backup of the homes, and nothing of a Household leaves the server but what is sent to Wilma, MyClub, the model and the Recipients as described above.

## Reporting a security problem

Please don't open a public issue. Report it privately through GitHub: on this repository's **Security** tab, click **Report a vulnerability**. Only the maintainers can see the report. Include what you found, how to reproduce it, and what it exposes. We'll reply there and credit you when the fix is released, unless you'd rather stay anonymous.
