# Security and privacy

Parent Recap runs on the Household's own Mac, or Windows PC ([On Windows](#on-windows)). The program reads each Source from that Mac, sends what it read to the model the Household chose, and emails the Brief from Parent Recap's own address, `brief@parentrecap.com`, through the maintainers' gateway (ADR 0032). The Household's Gmail, when it has one connected, is only read. The only Parent Recap server is the maintainers' gateway: every Household sends its Briefs through it, and a Household that chose it as its AI sends its model calls there too (see [The maintainers' gateway](#the-maintainers-gateway)). The same server also runs the program itself for a Household the maintainers host because it has no computer to run it on, and then keeps its Wilma login, MyClub links, config and Briefs (see [The hosted version](#the-hosted-version)). This page lists where data goes and where every secret lives, so you can decide before installing whether to trust it with your Household's messages.

## How data flows

Each evening the scheduled job on your Mac does the following. For a Hosted Household the same job runs on the maintainers' server instead, as the Household's own Linux user, and reads only Wilma and MyClub: its path is in [The hosted version](#the-hosted-version).

### Reading the Sources

| Source                   | How it's read                                                                                                                                                                | What leaves the Mac                                      |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| Gmail                    | IMAP to Google, using your App Password. Only senders on your allowlist are fetched; mail you sent yourself, drafts, Promotions and Social are skipped.                      | Nothing new: the mail is already at Google.              |
| Wilma                    | The unofficial community [wilma CLI](https://github.com/aikarjal/wilmai) logs in to your school's Wilma server as you and returns messages, announcements and the timetable. | Your Wilma login, sent by the CLI to the Wilma server.   |
| WhatsApp                 | As a Linked Device, paired on the setup page the way WhatsApp Web is (ADR 0027). Only the messages of the groups you picked are kept.                                        | Nothing new: the messages already come through WhatsApp. |
| MyClub                   | Your personal calendar subscription link is downloaded.                                                                                                                      | The link, including its personal token, sent to MyClub.  |
| Weekend Picks (optional) | Public events are fetched from the Helsinki region's Linked Events API.                                                                                                      | Nothing about your Household.                            |

### Summarizing

Everything read above for that evening, plus your Kids' names and aliases (as Kid A, Kid B while the AI filter is on, unless you ask for their names to go as they are) and the Weekend Picks preferences you configured, goes to the model you chose, cut down first on your Mac as [What the AI sees](README.md#what-the-ai-sees) describes:

- **Claude** (`llm.backend: claude`): through the `claude` CLI to Anthropic, under your Claude subscription or API key. Each call runs in an empty temporary folder with no tools, no MCP servers and none of your own Claude settings, so the model can't run commands or read files. The prompt goes to the CLI on standard input, not on its command line, so other accounts can't see it in the process list. The session isn't saved, so nothing is left under `~/.claude/projects`.
- **ChatGPT** (`llm.backend: codex`): through `codex exec` to OpenAI, under your ChatGPT account. Each call runs in an empty temporary folder with a read-only sandbox, with Codex's shell, command execution, apps and plugins turned off, so the model can't run commands or read files. The prompt goes on standard input, the session isn't saved, and your own Codex configuration and MCP tools aren't loaded.
- **Parent Recap's gateway** (`llm.backend: gateway`, invited Households only): the program itself sends each call over HTTPS to the maintainers' gateway, with your Gateway Key, and the gateway passes it on to Anthropic under the maintainers' account. Neither Claude Code nor Codex runs. See [The maintainers' gateway](#the-maintainers-gateway).

How long Anthropic or OpenAI keep that data, and whether they train on it, is set by your account with them, not by Parent Recap. On consumer plans both may train on your chats by default, and the setup page says where to turn that off. Through the gateway, the account is the maintainers' Anthropic API account, under Anthropic's [Commercial Terms](https://www.anthropic.com/legal/commercial-terms) (section B: "Anthropic may not train models on Customer Content from Services"; [Anthropic's privacy centre](https://privacy.claude.com/en/articles/7996868-is-my-data-used-for-model-training) says the same of its API), which don't let Anthropic train its models on what is sent.

### The maintainers' gateway

Every Household has a Gateway Key to the gateway the maintainers run: every Brief is sent through it (ADR 0032). A Household whose AI is its own Claude Code or Codex gets a key for sending only from the gateway itself, bound to its Recipients, each of whom confirms their address by email before the gateway sends them anything (ADR 0033); an invited Household without a Claude or ChatGPT subscription can have the gateway write the Brief too, with the maintainers paying for its model calls, and gets that key from the maintainers (ADR 0014). A Household should know what that means before installing. Its deployment config is public in [`ops/gateway/`](ops/gateway/README.md) (ADR 0015).

- **What passes through it:** for a Household that has it write the Brief, every model call of the evening Brief, its translations and Weekend Picks, as described above, so after the AI filter when it's on: the messages' text, with your Kids as Kid A, Kid B and other people's names, phone numbers, email addresses and links as placeholders. Also your Gateway Key, in each call's `x-api-key` header, and the small test calls setup and `doctor` make. Every Household, whatever its AI, sends it each Brief, Weekend Picks and first Brief from setup as the Recipients read them, with the Recipients' addresses and the `.ics` attachment, and the Gateway Key they're sent with; see [Delivering](#delivering). Nothing else of your Household, such as your passwords or your config, is sent to it.
- **What it keeps of a key for sending only (ADR 0033):** the key, and the Recipients' addresses bound to it, each with its language and whether and when it was confirmed, so that the gateway sends only to them. Nothing else of your Household. When the program asks for such a key, or binds changed Recipients, it sends the gateway the Recipients' addresses and languages, and the gateway emails each of them a confirmation link from `brief@parentrecap.com`. To rate-limit these requests it counts them for a day by a one-way hash of the caller's IP address and of each address, and keeps no IP address.
- **What it keeps:** for each call, the Gateway Key it came with, the model, the number of tokens, the cost, the HTTP status and the time, for 90 days. It doesn't keep the request or reply text: content logging is off, and a request can't turn it on. Of a Brief it sends it keeps nothing: one log line with the key's name, the number of Recipients, the size and the outcome, never the subject, the text, the attachments or the addresses, and a count of the key's sends that day. Its web server keeps no access log. Its database holds each Gateway Key, which the maintainers' admin login can read, under a neutral label; which Household holds which key is known only to the maintainers.
- **Where it runs:** on an Oracle Cloud virtual machine in Stockholm, Sweden (EU), running the open-source [Bifrost](https://github.com/maximhq/bifrost) gateway (ADR 0016) behind the Caddy web server. Only its `/v1/messages` and `/v1/brief` addresses (with `/v1/brief/key` and `/v1/brief/recipients`, which make and bind keys for sending only, the Brief's stop page and confirmation page, and the hosted version's sign-up page) are reachable from the internet, over HTTPS; its admin interface is reachable only from the server itself. From there each call goes to Anthropic's API, and each Brief to OCI Email Delivery in the same Oracle Cloud region, which keeps no message content, only bounces, complaints and delivery counts.
- **What the maintainers can do with a key:** each key is capped at $0.10 a day and at 4 Briefs sent a day, and the maintainers can turn it off at any time. A call past the cap or with a turned-off key fails, and that evening's Brief says its Digest couldn't be written. A send past the cap or with a turned-off key fails too: no Brief goes out that evening, the log says why, and the night's messages come in the next Brief.

Switching to Claude or ChatGPT with `manage` stops the model calls to the gateway from the next Brief on; the Brief is still sent through it. Uninstall removes the Gateway Key from the Keychain. To have a key turned off, ask the maintainers who sent it.

### Delivering

- For every Household (ADR 0028, ADR 0032), the program posts each Brief, Weekend Picks and the first Brief from setup, with its Recipients' addresses and attachment, over HTTPS to the maintainers' gateway with your Gateway Key, and the gateway hands it to OCI Email Delivery, which sends it from `brief@parentrecap.com`. Neither keeps the message (see [The maintainers' gateway](#the-maintainers-gateway)). New calendar events go with it as an `.ics` attachment. Nobody reads that address: the Brief says so and names the setup parent's address to write to instead. Your Gmail and its App Password are never used to send; they're needed only if the Gmail Source reads your mail. Without a Gateway Key no Brief can be sent: a Household whose AI is its own Claude Code or Codex gets one for sending from the gateway (ADR 0033), and the Brief goes only to the Recipients who confirmed their address through the link in the gateway's email; `doctor`, the setup page and the evening run's log say whom the email went to. A Household whose AI is the gateway asks the Parent Recap team for its key.
- In Google Calendar mode, new events are written to your calendar through the Google Calendar API instead.
- If the pilot feedback links are turned on, clicking ⭐ or ❌ in a Brief opens a pre-filled Google Form owned by the Parent Recap maintainers. The link carries that item's text as the AI saw it, with other people's names, phone numbers, email addresses and links as placeholders, its Source, the model, the date, a pseudonym made from your Household label on the Mac, and the Kid as Kid A or Kid B. Opening the link sends these fields to Google as part of the address, and the maintainers receive them only if you press submit.

### What stays on the Mac

- `~/.family/config.yaml`: your configuration, including Kids' names, allowlisted senders, chosen WhatsApp chats and MyClub links. Setup creates it owner-only (`chmod 600`), inside `~/.family`, which the installer makes owner-only (`chmod 700`).
- `~/.family/state.json`: which messages and events were already handled, and when a Brief last went out to each Recipient's address.
- `~/ParentRecap/`: every Brief as Markdown, plus the raw messages it was built from (`*.raw.json`), Weekend Picks under `weekend_events/`, logs and model diagnostics under `~/ParentRecap/logs/`, and `held-back-list.txt`, the list of held-back messages that `parent-recap ai-filter-report --held-back` opens in TextEdit. These are not encrypted beyond your Mac's own disk encryption.

Everything Parent Recap writes is owner-only: files `600`, folders `700`, so other accounts on the same Mac, such as a Kid's own account, can't read them. The installer makes `~/ParentRecap` owner-only, the program and its scheduled jobs create files with umask `077`, and each run takes group and other access off the archive, log, Weekend Picks and `~/.family` folders and the files in them (such as config backups), which also fixes installs from before 0.4.0.

### The setup page

`parent-recap setup page` serves the setup page from the Mac itself, only while setup needs it. It listens on 127.0.0.1, so no other computer can reach it, on a free port. Its address carries a one-time random code that every request must have, except the browser's own request for its tab icon, which gets an empty answer, and it refuses a request whose Host or Origin isn't its own address, so a website open in the browser can't use it. It serves only the program's own page files, which load nothing from the internet, and it logs nothing about requests. It stops after 30 minutes without a request.

To build the check page, it reads only the senders of the last 60 days of Gmail (their domains and one sender name each), never the mail, and keeps them in setup's progress, `~/.family/setup-progress.json`, which is owner-only. It never offers a public mail service such as gmail.com for the allowlist, so private mail isn't read. The health check it runs returns only each check's name and status to the page, never the details, which can quote an address or an error.

For the first Brief, it makes the real Brief through a `bg` job, as `parent-recap run --preview` does, which sends nothing and writes no archive or state, only one line in the evening job's log with counts: each Source's messages, the held-back ones, and the Digest's length and its Notices, Action Items and new events, with no message text, names or subjects. The Brief stays in Parent Recap's memory and is shown in a sandboxed frame on the page that runs no scripts and opens no links. "Send it to me" emails it to the setup parent only, the first Recipient, and records only that it reached them. For a pilot Household, "Something's wrong, tell us" opens the same pre-filled feedback Form link as the Digest's ❌ in the Brief, with the same data in it (see the pilot feedback section of `docs/config.md`).

At Finish, it installs the evening job and the Mac's wake-up as `parent-recap schedule install` does. The Mac password goes into macOS's own administrator dialog, never the page, and the page has no field for it. Another repeating wake schedule on the Mac is replaced only once the parent presses Replace it. It then checks the outcomes as `parent-recap setup status` does and returns only each outcome and whether it's true, never the reasons, which can name an address. Once every outcome is true, the server stops.

### Where MyClub links can appear

A MyClub calendar link carries a personal token that lets anyone read the Kid's club calendar. The parent pastes it into a macOS dialog with hidden input (`parent-recap setup myclub`), into the setup page's own password field (ADR 0007), or into their own Terminal with the older `scripts/setup_myclub.py`, never into the Claude or Codex chat, and it's kept only in `~/.family/config.yaml` and the config backups next to it in `~/.family`. Each night it's sent to MyClub to download the calendar. When the download fails, `doctor`, the logs, the archive and the Brief name only the MyClub server and the HTTP status, never the link's path or token.

Parent Recap writes and reads its Keychain items only with `/usr/bin/security`. It types each secret into `security -i` on stdin, never on a command line, and stores the item so that `/usr/bin/security` may read it without asking for the Keychain password (ADR 0009). Other programs, including Parent Recap's own Python, get macOS's prompt.

On Windows the secrets go into Credential Manager instead, and any program run as the same Windows user can read them: see [On Windows](#on-windows).

`parent-recap uninstall` deletes every secret in this table that Parent Recap stored. Of the wilma CLI's file it removes only the sign-in setup made, and with it every Wilma session the CLI saved, as the CLI does when it removes a sign-in. It leaves the ChatGPT login (Codex's) and a Wilma sign-in that was there before setup, with the CLI's sessions if it removed no sign-in, and never touches your accounts: delete the Gmail App Password and any Google Calendar access in your Google account. A Hosted Household's go when the maintainers remove it ([The hosted version](#the-hosted-version)). What each setup step writes, and how uninstall removes it, is in [docs/setup-internals.md](docs/setup-internals.md).

Keep `~/.family` and `~/.config/wilmai` out of cloud sync, dotfiles repos and backups you share. How to remove the Wilma file when you stop using Parent Recap, and what to do if it may have leaked, is in [docs/sources.md](docs/sources.md#where-the-wilma-password-is-stored).

## On Windows

On a Windows 11 PC ([Parent Recap on Windows](docs/windows.md), ADR 0019) data flows as above, and the setup page works the same way. What differs is where things are kept and who on the PC can read them.

- **The secrets** (the Gmail App Password, the Gateway Key and the Claude token) go into Credential Manager, one generic credential each, named `Parent Recap/<account>` with the accounts above (Control Panel → Credential Manager → Windows Credentials). They're kept on this PC for this Windows user and never roam to another PC. Parent Recap writes and reads them through Windows' own Credential Manager functions, never on a command line, and the setup page takes them in its own fields as on a Mac.
- **Any program you run as the same Windows user can read them without asking.** Windows has no counterpart to the Keychain's per-program trust (ADR 0009): a program you run under that account, including one you shouldn't have trusted, gets the Gmail App Password, the Gateway Key and the Claude token (ADR 0021).
- **The files** are in `%LOCALAPPDATA%\ParentRecap` (the program, its own Python and Node, the install's logs), `%USERPROFILE%\ParentRecap` (the archive, the evening run's logs, the wilma CLI), `%USERPROFILE%\.family` (the config and state), `%USERPROFILE%\.config\wilmai` (the wilma CLI's sign-in, **not encrypted** as above) and Codex's `%USERPROFILE%\.codex`. The owner-only permissions above don't apply on Windows, where Python can set only a file's read-only flag ([Python's `os.chmod`](https://docs.python.org/3/library/os.html#os.chmod)). Parent Recap sets no permissions of its own there, so who else on the PC can read these folders is whatever Windows allows for the rest of your user folder.
- **The evening run** is a Task Scheduler task that runs as you, only while you're signed in (ADR 0021). Setup never asks for your Windows password, stores none, and needs no administrator rights.
- **The install line** runs `install.ps1` from the `stable` branch, which isn't signed yet. It checks the Python and Node it downloads against the SHA-256 checksums pinned in it. On the setup page, ChatGPT's Codex CLI is installed with OpenAI's own installer, and Claude Code with Anthropic's.
- **Uninstalling** removes the `Parent Recap/…` credentials from Credential Manager with the rest ([Uninstalling](docs/windows.md#uninstalling)). Delete the Gmail App Password in your Google account yourself.

## The hosted version

A Household with no computer to run Parent Recap on can ask the maintainers to host it (ADR 0029). Only Households the maintainers invite are hosted: they send an Invite Link, and the family signs up on its phone (ADR 0031). The program then runs for it on the gateway's server in Stockholm ([The maintainers' gateway](#the-maintainers-gateway)). That is a bigger step than the gateway: the gateway keeps nothing of a Household's messages, while for a Hosted Household the maintainers hold its Wilma login and its Briefs on a server they administer, and so process its Kids' school messages on its behalf under GDPR. A Household that would rather keep them at home runs the program on its own Mac or Windows PC instead.

### How data flows when hosted

- **Signing up.** On the sign-up page, over HTTPS, the family types its Wilma town and login, checks the Recipients the maintainers prefilled, and pastes each Kid's MyClub link or leaves it empty. The sign-up service signs in to Wilma with that login and reads the Kids before anything is made, and downloads each MyClub link once to check it. Until the Household is made, the answers, the Wilma password among them, are kept only in the service's memory: after 30 minutes they can't be used and the family signs in again, and they're dropped at the next sign-up or when the service restarts. Then it makes the Household's own Linux user, mints its Gateway Key, writes the config, the Wilma sign-in and the key in that user's home, installs the evening job, and has the first Brief made and sent. Meanwhile the page asks the service every few seconds which of these steps has ended; the service keeps only that and how the sign-up ended, nothing secret, in memory until the page has seen it, for a day at most. The service never logs a request's address or body: its log says, for each sign-up, the Household's label and evening time, or which step wasn't taken and why, never the password, a link or an address.
- **Each evening.** The evening job runs as the Household's Linux user, at its own time from 21:00, held to half a CPU core and 400 MB of memory. It reads Wilma and MyClub as in [Reading the Sources](#reading-the-sources), from the server's address, so Wilma sees every Hosted Household sign in from the same datacenter. Its model calls go through the gateway with its Gateway Key ([Summarizing](#summarizing)), and the gateway sends the Brief from `brief@parentrecap.com` ([Delivering](#delivering)), with new events as an `.ics` attachment.
- **Not read.** WhatsApp: the server holds no Linked Device, because its session reads all of a parent's chats and can send as them (ADR 0029). Gmail: the hosted version has no Gmail step, so it holds no App Password and reads no mail.

### What the maintainers hold, and for how long

For each Hosted Household, in the home of its Linux user `ph-…` (8 random hex digits, a label that names no one):

- its Wilma login and session, its MyClub links and its Gateway Key, as in [Where each secret lives](#where-each-secret-lives);
- its config, `~/.family/config.yaml`: the Kids' names, schools and classes as Wilma lists them, the Recipients' addresses and languages, and the evening time, with `state.json` as on a Mac and `last-run.json`, when the last run ended and how, how long it took and its peak memory;
- its archive, `~/ParentRecap/`: every Brief, the Wilma and MyClub messages it was built from, and the logs, as in [What stays on the Mac](#what-stays-on-the-mac).

All of it is kept until the Household is removed; the archive isn't trimmed, and only `state.json` drops what it records after 45 days. A Household has no setup page or `manage`: to change a setting it asks the maintainers, who edit its config, and to leave it asks them to remove it. Removing it ([Remove a Household](ops/gateway/README.md#hosted-households)) turns off its evening jobs, revokes its Gateway Key and deletes its Linux user with its home, and so everything above. What stays are log lines with nothing of the family in them: the journal's lines naming its label, and the gateway's per-call token counts and cost.

Outside the homes, the sign-up service keeps each Household's label and evening time, and each Invite Link with its prefilled Recipients' addresses until a Household is made from it. A link that expires unused keeps them until a maintainer deletes it.

### Who can read it

- **The Household's own Linux user.** Everything above is owner-only, files `600` and folders `700`, in a home only that user can open, so another Household's user can't read it. The secrets are owner-only files, since a server has no Keychain (ADR 0030): they have the protection the Wilma login has on a Mac, no more.
- **The sign-up service.** It may run, as any Hosted Household's user, only the commands it needs to make the Household, check its status and remove it, each with exactly its arguments ([`signup.sudoers`](ops/gateway/signup.sudoers)): the release's `install.sh`, and the Household's own `parent-recap` with `signup household`, `run --first-brief`, `signup health` and `schedule uninstall`. So even a compromised service can't read the files that hold a Household's Wilma password, MyClub links or Gateway Key. It could still rewrite a Household's config through `signup household`, its Recipients among them, and send it a first Brief. Its status command prints each Household's last run and the statuses of `doctor`'s checks, never message text, subjects, addresses or names.
- **The maintainers who administer the server.** Root reads every Hosted Household's files, secrets included. The server's disk is encrypted only as Oracle encrypts its volumes, so it doesn't keep the data from Oracle as the host. The maintainers' AI assistant has a login on the server that reads logs and service status, but has no sudo and can't open a Household's home.
- **No one else.** The setup in [`ops/gateway/`](ops/gateway/README.md) makes no backup of the homes, and nothing of a Household leaves the server but what is sent to Wilma, MyClub, the model and the Recipients as described above.

## Reporting a security problem

Please don't open a public issue. Report it privately through GitHub: on this repository's **Security** tab, click **Report a vulnerability**. Only the maintainers can see the report. Include what you found, how to reproduce it, and what it exposes. We'll reply there and credit you when the fix is released, unless you'd rather stay anonymous.
